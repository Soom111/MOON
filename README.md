# SHINE UpSeller 云端采集 / Coleta na nuvem

此程序在 Render 运行，个人电脑关机不影响云端任务。需要完成独立云端浏览器的首次登录，并连接网站与调度器；仅上传源代码不代表已启用自动更新。

## 部署

1. 将本目录单独放入自己的私有 GitHub 仓库。不要上传网站仓库、业务数据、环境变量、密码或登录状态。
2. Render 创建 Docker Web Service，使用本目录的 Dockerfile，初次测试采用 Free。服务监听 `$PORT`，健康检查 `/health`。
3. 设置 `SITE_URL` 为现有 SHINE 网站 HTTPS 根地址；`COLLECTOR_TOKEN` 使用至少32字符的随机密钥。
4. 网站保存同一密钥为秘密变量 `PARCEL_COLLECTOR_TOKEN`，另保存32字节随机值的Base64为秘密变量 `PARCEL_COLLECTOR_STATE_KEY`。这些值不放进前端、Git或Docker构建参数。
5. 在网站 `/collector` 由负责人保存 Render 地址与5个完整店铺名，再打开“登录UpSeller”。网页登录控制30分钟后失效，入口链接90秒有效且只能使用一次。
6. 用户亲自在云端画面中输入账号密码并处理验证码；程序不自动破解验证。登录完成后操作控制关闭，点击“开始采集”，通过真实数据核对后启用独立的10分钟调度。已有FULL/ULOCK调度不作替换。
7. Supabase Cron 仅调用网站 `/api/collector/tick`，以独立Vault密钥鉴权。网站限制自动采集为圣保罗07:30–19:30，手动采集不受时段限制。每轮最多8分钟，重叠请求返回busy。

登录状态和跟踪清单通过认证接口持久保存于网站私有R2对象，并用AES-GCM加密。Render休眠或重启后从网站恢复，不依赖本地硬盘。UpSeller若使会话失效，必须由负责人重新登录；旧数据仍保留。

## 统计口径

- 最晚发货日期筛选为今天结束，起始为此前90天，包含该范围内逾期待处理包裹。更早记录不在本轮查询范围内。
- 首次采集建立当天待处理包裹的跟踪清单，之后新增包裹加入；首次采集前已发货的历史包裹不在这个待交接任务的总数中。界面显示开始跟踪的时间，避免误认为完整历史发货报表。
- 以`UPA`包裹ID去重，不按SKU行或商品件数累计。
- 按负责人确认的完整店铺名匹配，再区分Coleta/Flex/Agência。未知店铺或物流方式会停止发布并提示核对，不猜测分配。
- 未打印、已打印未扫描、异常为未扫描；待揽收、确认已发货为已扫描。离开列表不等于已发货：必须逐ID在近期订单查询确认。已跟踪的发货/取消状态也会再次核实。
- 每页数量、分页总数、筛选条件、分类数量和明细必须一致；任一失败保留旧数据。网站以单个数据库事务发布全部店铺；与司机交接并发冲突时拒绝本轮并等待下次采集。
- 无变化时不重写数量和明细，仅更新最后成功检查时间。
- 实际交给司机的数量是网站的独立交接流水。其他人只能填写本次交接数和姓名，采集不会更改这些流水。

## 验证

```sh
python -m unittest discover -p 'test_*.py' -v
```

纯规则、鉴权和持久化接口已设置测试；真实账号登录、Render内存占用、UpSeller分页和每次登录后的页面差异，必须在实际服务完成首轮采集后核对。Free计划用于可行性测试，不能据此承诺生产稳定性。
